# Ngày 24/9/2026: Bổ sung kiến trúc Temporal Attention (Thay thế Mamba)

## 1. Vấn đề của module Mamba hiện tại
- Phụ thuộc thư viện `mamba_ssm` (cần biên dịch CUDA, khó cài đặt trên một số môi trường như Jetson).
- Khi không có `mamba_ssm`, hệ thống dùng `SimpleS6Block` (fallback) chạy bằng PyTorch thuần. Mặc dù chạy được nhưng kém tối ưu về tốc độ.
- Với bài toán hiện tại, độ dài chuỗi frame khá ngắn ($L \in [4, 16]$). Do đó, chi phí $O(L^2)$ của Self-Attention không hề đáng kể, trong khi Attention cung cấp khả năng quan sát hai chiều (bidirectional) tự nhiên và tốt hơn so với cách của Mamba hiện tại (phải lật ngược chuỗi thủ công).

## 2. Giải pháp: Temporal Attention Encoder
- Triển khai `TemporalAttentionEncoder` như một **drop-in replacement** hoàn hảo cho `TemporalMambaEncoder`.
- **Interface giữ nguyên**: Input `[B, N, d_in]`, Output `([B, d_out], [B, N, d_model])`. Hỗ trợ đầy đủ PE (Positional Embedding) và Attention Pooling (`attn`).
- **Kiến trúc**: 2 layers Transformer Encoder (8 heads, Pre-LN, GELU, dropout 0.1) được tối ưu sâu bởi PyTorch (`nn.TransformerEncoderLayer`).
- **Kích thước model**: Attention module có khoảng **8.04M** tham số, nhỉnh hơn một chút so với Mamba module (**5.0M** tham số), nhưng tốc độ inference có khả năng tốt hơn nhờ tối ưu hoá Native Transformer của PyTorch.

## 3. Các thay đổi trong Codebase
1. **`model.py`**:
   - Thêm class `TemporalAttentionEncoder`.
   - Chỉnh sửa class `UAVReIDNet` để nhận tham số `temporal_type`. Khởi tạo `TemporalAttentionEncoder` nếu `temporal_type='attention'`, ngược lại giữ `TemporalMambaEncoder`.
2. **Cập nhật toàn bộ các file Pipeline**:
   - Chỉnh sửa hàng loạt file để đọc `temporal_type` từ config và truyền vào `UAVReIDNet`:
     - `train_reid.py`
     - `infer.py`
     - `evaluate_reid.py`
     - `evaluate_reid_robustness.py`
     - `calibrate_threshold.py`
     - `phan_rang/infer_realworld.py`
3. **Cập nhật Config (`configs/config_jetson.yaml`)**:
   - Bổ sung `temporal_type: "attention"` vào các mục `train`, `infer`, và `infer_robustness`.

### 7.5. ❌ ĐÍNH CHÍNH: cửa sổ SOFT LOCK là `N` frame, KHÔNG phải 45

Bản đầu của §7.3 tôi viết *"cửa sổ soft-lock cần 45 frame LIÊN TỤC = (N−1)·stride+1"*.
**SAI.** Đọc `infer.py:282-285` mới thấy có **HAI cửa sổ khác nhau**:

```python
self.soft_lock_buffer = SlidingWindowBuffer(self.num_frames, stride=1)      # (1)
self.hard_lock_buffer = SlidingWindowBuffer(self.num_frames, self.stride)   # (2)
```

`SlidingWindowBuffer(window_size, stride)`:
- `stride` quyết định **tần suất NẠP** frame (`should_extract()`: `frame_counter % stride == 0`)
- `is_ready()` ⇔ `len(features) >= window_size`

| Cửa sổ | Tham số | Nạp frame | Cần | Vai trò |
|---|---|---|---|---|
| **SOFT LOCK** | `SlidingWindowBuffer(N, stride=1)` | **mỗi** frame | **`N` frame LIÊN TỤC** | chọn ứng viên / xem điểm, KHÔNG chốt |
| **HARD LOCK** | `SlidingWindowBuffer(N, stride=s)` | mỗi `s` frame | **`N` mẫu** ⇒ `(N−1)·s+1` frame video | mới là cửa sổ đem so với Memory Bank |
| Memory Bank / tracking | `SlidingWindowBuffer(N, stride=s)` | mỗi `s` frame | `(N−1)·s+1` | khớp bước thời gian lúc train |

**⇒ Bạn đúng, tôi sai.** `(N−1)·s+1` là cửa sổ **HARD LOCK**, không phải soft lock.

**Hệ quả:** `t2_search_gap_tolerance` bảo vệ cửa sổ **HARD LOCK** (cửa sổ dài), không phải
cửa sổ soft lock. Lý do vẫn đúng: nếu reset ngay ở 1 frame vắng thì các event tái xuất ngắn
hơn `(N−1)·s+1` frame sẽ **vĩnh viễn không lock được**.

**🐛 Comment trong code cũng SAI (stale):** `infer.py:296` viết
```
# `soft_lock_buffer` cần `(num_frames-1)*stride+1` frame LIÊN TỤC (12/4 -> 45), mà
```
Comment này viết **trước** khi tách 2 cửa sổ (22/9) và chưa cập nhật — đúng ra phải là
`hard_lock_buffer`. Chính comment sai này làm tôi kết luận nhầm. **ĐÃ SỬA trong `infer.py`.**
